= Recover data after a ransomware attack with ONTAP ARP/AI
:icons: font
:imagesdir: ../media/

[.lead]
Autonomous Ransomware Protection with AI (ARP/AI) creates snapshots to protect against ransomware threats. You can use ARP/AI snapshots or another snapshot of your volume to restore data.

NOTE: If you are running ONTAP 9.15.1 or earlier, see link:recover-arp.html[Recover data after a ransomware attack with ARP].

.About this task

Depending on the potential attack situation, you'll restore data in one of these ways:

* *<<restore-from-arp-snapshot,Restore from the most recent ARP/AI snapshot>>*: Use the most recent ARP/AI snapshot available when you have confidence in its integrity.
* *<<restore-from-earlier-snapshot,Restore from an earlier snapshot>>*: Release the lock on the most recent ARP/AI snapshot and then restore from an earlier snapshot.
* *<<restore-without-attack,Restore when no attack is reported>>*: First restore from the most recent ARP/AI snapshot then complete a subsequent restoration from the snapshot you choose.

ARP/AI creates snapshots with one of the following prepended names:

* `Anti_ransomware_periodic_backup`: Used in ONTAP 9.17.1 and later for snapshots created at regular 4-hour intervals. For example, `Anti_ransomware_periodic_backup.2025-06-01_1248`.
* `Anti_ransomware_attack_backup`: Used in ONTAP 9.17.1 and later for snapshots created in response to abnormalities. These snapshots have a default retention of 10 days. For example, `Anti_ransomware_attack_backup.2025-08-25_1248`.
* `Anti_ransomware_backup`: Used in ONTAP 9.16.1 and earlier for snapshots created in response to abnormalities. For example, `Anti_ransomware_backup.2022-12-20_1248`.

.Before you begin
* If you are responding to an abnormal activity warning, link:respond-arpai.html#classify-as-potential-ransomware-attack-and-recover-data[you must first categorize it as a potential ransomware attack] before proceeding with data restoration.
* Choose a <<choose-a-recovery-method,restore method>> and review <<recovery-constraints-and-considerations,recovery constraints>> before you complete a restore procedure.

[[choose-a-recovery-method]]
== Choose a recovery method

Depending on the extent of data corruption and your operational requirements, choose one or a combination of these recovery methods.

* *Volume snapshot restore*: Rolls back the entire volume to a selected snapshot (ARP/AI or scheduled). This is the fastest method but removes all snapshots created after the restore point.

* *FlexClone from a clean snapshot*: Creates a clone volume from the selected snapshot, preserving the original volume and all its snapshots for forensic analysis or additional recovery. It is recommended to split the clone from the parent volume to isolate the infected parent from the clean clone.
+
Learn more about link:../volumes/create-flexclone-task.html[creating a FlexClone volume from a snapshot] and link:../volumes/split-flexclone-from-parent-task.html[splitting a FlexClone from its parent].

* *Single-file SnapRestore*: Restores individual files from snapshots. Each file can be sourced from a different snapshot. This is practical when the number of affected files is relatively small.
+
Learn more about link:../data-protection/restore-single-file-snapshot-task.html[restoring a single file from a snapshot].

* *Data copy from the `.snapshot` directory*: Copies data from the snapshot mount point to a new volume using standard file copy operations. This method preserves the original volume and snapshots for analysis.

* *Hybrid approach*: The volume is first rolled back to the closest clean snapshot using SnapRestore, then any remaining corrupted files are restored individually from another snapshot or external backup.

[[recovery-constraints-and-considerations]]
== Recovery constraints and considerations

* For ONTAP 9.16.1 and later: Clear the suspected event *first* (in link:respond-arpai.html[Respond to abnormal activity]) and then perform the restore. After clearing, ARP/AI snapshots are retained based on how you categorize the activity. Beginning with ONTAP 9.17.1, the defaults are 7 days (real attack) or 24 hours (false positive). In ONTAP 9.16.1, the defaults are 5 days (real attack) or 48 hours (false positive). The clear-suspect option becomes unavailable after a volume restore, so you must clear before restoring.
* Releasing the ARP/AI snapshot lock is only required when you use `volume snapshot restore` to restore from an earlier snapshot. It is not required for FlexClone, single-file SnapRestore, data copy operations, or similar methods.
* For SAN volumes where the attack is detected by entropy analysis alone, only the snapshot created just before the attack timeline and the attack snapshot are retained for an extended period (10 days by default, configurable). Other periodic snapshots continue to follow normal retention rules. This differs from NAS volumes, where all snapshots created before the attack timeline are retained until the administrator performs a clear-suspect action.

.SnapMirror considerations
* If the volume is part of a SnapMirror synchronous or SnapMirror active sync SAN relationship in ONTAP 9.19.1 and you plan a volume-level restore, quiesce or link:../data-protection/make-destination-volume-writeable-task.html[break the relationship before restore] and then re-establish protection after restore.
* If you restore an ARP/AI-protected volume from a snapshot while it participates in a SnapMirror relationship, manually update all mirror copies after the restore. Otherwise, mirror copies can become unusable and might need to be deleted and recreated.

For full SnapMirror and ARP/AI interoperability behavior, see link:support-arpai.html#snapmirror[SnapMirror and ARP/AI interoperability].

[[restore-after-system-attack]]
== Restore after a system attack

For volume snapshot restores, choose one of these flows depending on the snapshot source and situation:

* <<restore-from-arp-snapshot,Restore from the most recent ARP/AI snapshot>>
* <<restore-from-earlier-snapshot,Restore from an earlier snapshot>>
* <<restore-without-attack,Restore when no attack is identified>>

[[restore-from-arp-snapshot]]
=== Restore from the most recent ARP/AI snapshot

Choose this flow when you can confidently restore from the most recent ARP/AI snapshot, which is the most up-to-date snapshot available for recovery.

[role="tabbed-block"]
====
.System Manager
--
. Select *Storage > Volumes*, then select the volume and *Snapshot Copies*.

. Before you run a volume restore, link:respond-arpai.html#arp-snapshot-decision-sm-pre-restore[clear suspected files].
+
NOTE: After you clear suspect files, the ARP/AI snapshot is retained for 7 days (by default). If you need more time for data recovery, link:modify-snapshot-options-arpai.html[adjust ARP/AI snapshot settings] to increase the retention time. After all data recovery is done, you can decrease the retention time.

. Select image:icon_kabob.gif[Menu options icon] next to the most recent ARP/AI snapshot (`Anti_ransomware`) you want to restore, then select *Restore*.
--

.CLI
--
. List the snapshots in a volume:
+
[source,cli]
----
volume snapshot show -vserver <svm> -volume <volume>
----

. Before you run `volume snapshot restore`, link:respond-arpai.html#arp-snapshot-decision-cli-pre-restore[clear suspected files].

. Restore the contents of a volume from a snapshot:
+
[source,cli]
----
volume snapshot restore -vserver <svm> -volume <volume> -snapshot <snapshot>
----
--
====

[[restore-from-earlier-snapshot]]
=== Restore from an earlier snapshot

Choose this flow when you want to restore from an earlier snapshot. Release the lock on the most recent ARP/AI snapshot before restoring from the earlier snapshot.

[role="tabbed-block"]
====
.System Manager
--
. Release the lock on the most recent ARP/AI snapshot:
+
.. Select *Storage > Volumes*.
.. Select *Security* then *View Suspected File Types*.
.. Mark the files as "Potential ransomware attack".
.. Select *Update and Clear Suspected File Types*.

. Select *Storage > Volumes*, then select the volume and *Snapshot Copies*.

. Select image:icon_kabob.gif[Menu options icon] next to the earlier snapshot you want to restore, then select *Restore*.
--

.CLI
--
. Mark the attack as potential ransomware (`-false-positive false`) and clear suspect files to release the lock:
+
[source,cli]
----
security anti-ransomware volume attack clear-suspect -vserver <svm_name> -volume <vol_name> [<extension identifiers>] -false-positive false
----

include::../_include/restore-snapshots-cli.adoc[]
--
====

[[restore-without-attack]]
== Restore when no attack is identified

When no attack is identified, first restore from the most recent ARP/AI snapshot and then restore from an earlier snapshot.

[role="tabbed-block"]
====
.System Manager
--
. Select *Storage > Volumes*, then select the volume and *Snapshot Copies*.
. Select image:icon_kabob.gif[Menu options icon] then choose the most recent `Anti_ransomware` snapshot.
. Select *Restore*.
. Return to the *Snapshot Copies* menu, then choose the earlier snapshot you want to use.
. Select *Restore*.
--

.CLI
--
. Restore from the most recent ARP/AI snapshot first:

.. List the snapshots in a volume:
+
[source,cli]
----
volume snapshot show -vserver <svm> -volume <volume>
----

.. Restore the contents of a volume from a snapshot:
+
[source,cli]
----
volume snapshot restore -vserver <svm> -volume <volume> -snapshot <snapshot>
----

. Select the earlier snapshot you want to use and repeat the restore.

Learn more about `volume snapshot` in the link:https://docs.netapp.com/us-en/ontap-cli/search.html?q=volume+snapshot[ONTAP command reference^].
--
====
